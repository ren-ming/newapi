# Codex OAuth 失效与额度耗尽自动禁用设计

## 目标

针对 5 个独立 Codex 渠道，在上游明确返回以下错误时，自动禁用当前失效渠道，避免后续请求反复命中无效账号，同时让请求继续尝试其他可用渠道：

- HTTP 401，错误文本包含 `invalidated oauth token for user`
- HTTP 429，错误文本包含 `The usage limit has been reached`

本设计复用现有渠道自动禁用、渠道状态、通知和重试机制，不新增数据库字段，不改变其他供应商的认证错误处理规则。

## 范围与边界

### 纳入范围

- 仅处理当前请求实际选中的渠道。
- 仅在全局自动禁用开关开启且渠道 `AutoBan` 开启时执行。
- 401 和 429 必须分别与对应错误文本组合匹配。
- 禁用后使用现有自动禁用状态，并记录上游错误原因。
- 当前请求继续遵守现有重试机制，尝试其他可用渠道。

### 不纳入范围

- 不把所有 401 或所有 429 都视为永久失效。
- 不自动恢复渠道。
- 不新增多 Key 逻辑；当前 5 个账户保持 5 个独立渠道。
- 不修改渠道密钥的存储加密方案；字段级加密另行设计。
- 不改变手动禁用渠道的状态。

## 现有实现复用

错误在 relay 层解析为 `types.NewAPIError`，其中保留 `StatusCode` 和错误文本。`controller/relay.go` 的 `processChannelError` 已负责：

1. 记录渠道错误；
2. 调用 `service.ShouldDisableChannel` 判断是否自动禁用；
3. 异步调用 `service.DisableChannel`；
4. 按现有错误重试流程切换渠道。

`service.DisableChannel` 已负责检查渠道 `AutoBan`、调用 `model.UpdateChannelStatus` 设置自动禁用状态，并通知根用户。该链路继续作为唯一的渠道状态变更入口。

## 判断逻辑

在 `service.ShouldDisableChannel` 中增加两个精确组合规则：

```text
status == 401 && message contains "invalidated oauth token for user"
status == 429 && message contains "the usage limit has been reached"
```

匹配使用小写化后的错误文本，因此大小写变化不影响识别。错误文本应来自 `NewAPIError.Error()` 或其等价的完整错误表示，不记录或新增任何 OAuth token 内容。

现有通用自动禁用状态码和关键词逻辑必须保留其既有行为；但由于默认 401 范围可能使所有 401 自动禁用，实施时需要明确区分：新增规则不能依赖“401 状态码单独命中”来满足本需求，也不能因新增关键词使任意状态码误触发。运行时 Option `AutomaticDisableStatusCodes` 的行为和管理员现有配置需要在测试中覆盖。

## 数据流

```text
请求
  -> 选择 Codex 渠道
  -> 上游返回 401/429
  -> 解析 NewAPIError
  -> 精确状态码 + 文本匹配
  -> 异步更新当前渠道为自动禁用
  -> 记录原因并通知管理员
  -> 现有重试逻辑选择其他启用渠道
```

如果没有其他可用渠道，返回现有渠道不可用错误；不伪造成功响应，也不自动修改其他渠道。

## 并发、幂等与缓存

同一渠道可能被多个并发请求同时命中。实现必须满足：

- 复用 `UpdateChannelStatus` 的现有状态更新和缓存刷新机制；
- 自动禁用操作可重复执行，不得把自动禁用状态恢复为启用；
- 不因并发更新覆盖手动禁用状态；
- 如现有更新函数无法区分“状态未变化”，通知可出现有限重复，但不得引入循环通知或重试风暴；
- 不在 relay 响应解析器中直接写数据库，保持协议转换与渠道状态管理分层。

## 恢复策略

- OAuth token 失效：重新登录 Codex，更新对应渠道 Key，再由管理员手动启用。
- 使用额度耗尽：确认额度周期恢复后，由管理员手动启用。
- 不设置定时自动恢复，因为上游额度恢复时间不稳定。
- 不自动启用手动禁用渠道。

## 测试设计

采用表驱动单元测试覆盖：

1. 401 + `invalidated oauth token for user`：匹配；
2. 429 + `The usage limit has been reached`：匹配；
3. 401 + 其他文本：不因新增规则匹配；
4. 429 + 其他文本：不因新增规则匹配；
5. 文本大小写变化：仍匹配；
6. 全局自动禁用关闭：不匹配；
7. 渠道 `AutoBan` 关闭：状态不更新；
8. 非目标状态码携带目标文本：不因组合规则匹配；
9. 两个独立渠道中一个失效：只禁用命中的渠道；
10. 失效后重试：继续选择其他启用渠道。

测试不得使用真实 OAuth token、真实渠道密钥或生产数据库。

## 实施顺序

1. 在服务层集中实现精确状态码与错误文本判断。
2. 复用既有异步禁用和通知链路。
3. 增加服务层及重试路径的表驱动测试。
4. 运行格式化、目标包测试、全量 Go 测试及竞态检测。
5. 部署前确认全局自动禁用开关、5 个渠道的 `AutoBan` 和运行时状态码配置。

## 验收标准

- 两类目标错误能准确自动禁用当前渠道；
- 其他渠道仍可被重试选中；
- 非目标错误不会因本功能误禁用；
- 自动禁用关闭或渠道 `AutoBan` 关闭时不产生状态变更；
- 禁用原因可在后台识别；
- 并发错误不会导致状态回滚、缓存失效或重试循环；
- 未引入 OAuth token 泄露或日志明文记录。
